# 同伴支线接入变更注意事项

## Summary

本文档给项目成员和后续 agent 说明：当前“同伴支线事件”采用先在测试界面验证、后续接入第一幕主线的开发方式。该方式符合《第一幕大致剧本 V2》的模块化流程设计：主线节点负责推进剧情，玩法模块负责结算战斗、检定、小游戏、支线、信任值和 AI 自由对话。

## Key Changes

- 当前新增的是“布洛克·铁锅：回声菌林的求救声”测试版支线，用于验证同伴支线框架。
- 支线事件暂时入口在测试界面：`测试 -> 同伴支线事件`。
- 后端新增支线事件状态、选择结算、信任值、威胁值、污染值、奖励、 AI 反馈和自由对话接口。
- 前端支线测试页已改为复用主线视觉小说框架：`VisualNovelStage`、`ActionPanel`、`DialogueLog` 和 `DiceRollOverlay`。
- 当前支线 UI 应表现为主线同款：人物立绘居中、底部文本框逐句显示、下方行动栏、右上角对话日志和返回/重开按钮。
- 布洛克·铁锅当前临时映射到现有 `senluo` 立绘；后续如有专属布洛克立绘，只需替换立绘映射。
- 后端已收紧同伴支线 AI 提示词，并增加输出清洗，避免出现 `KP视角`、`末结算提示`、Markdown 加粗、角色状态标题等不应展示给玩家的文本。
- 本次不应提交运行缓存、数据库临时状态、构建产物、日志和 Playwright 临时文件。

## Development Direction

- 当前做法是正确的：先做可测试模块，再接入主线。
- 测试模块后续必须接入第一幕 V2 主流程，不能长期停留为孤立 Demo。
- 测试界面的支线页应尽量复用主线已有 UI 和交互组件，不再维护一套独立的大段日志面板。
- 后续接入主线时，应由主线流程决定何时触发支线，并把玩家选择的 2 名同行同伴传给支线系统。
- 支线系统返回结果后，主线继续推进到骨柱湿地、莱因、Boss 和结局。
- 信任值不改变第一幕结局分支，只影响语气、奖励、建议和结局反馈。

## Safety Notes

- 不要提交 `backend/.env` 或任何 API Key。
- 当前 `backend/.env` 如已被 Git 追踪，提交前必须从 Git 跟踪中移除，但保留本地文件。
- 不要提交 `data/game.db`、`frontend/node_modules/.vite`、`frontend/dist`、`logs`、`.playwright-cli` 等运行/构建产物，除非队友明确要求。
- 保留 `start.bat` 的本地启动修复价值：它使用 `backend/.venv` 启动后端，避免系统 Python 缺依赖。
- 运行 `npm run build`、浏览器自动化测试或本地试玩后，工作区可能出现构建产物和缓存变动；这些通常只是“运行后变脏”，不是要提交的源码。

## Low-Quota Collaboration Mode

为了减少 Codex 额度消耗，后续默认采用轻量协作方式：

- Codex 负责读代码、改代码、做必要的静态检查和构建检查。
- 玩家负责本地启动、完整试玩、截图和体验反馈。
- 除非正在排查“页面打不开、接口报错、构建失败、无法复现的严重 bug”，Codex 不默认跑完整浏览器自动化测试。
- 每轮反馈尽量集中 3-8 个问题一起提交，避免为单个小文本反复开启大范围代码阅读和测试。
- 反馈请优先给“操作步骤 + 看到的问题 + 希望改成什么 + 截图/原文”，这样 Codex 可以少猜测、少搜索、少重复测试。
- 如果只改文案、提示词、数值或按钮显示，通常只需要代码级检查；完整体验验收交给玩家试玩。
- 如果改动涉及 API、状态流转、战斗结算、存档或主线接入，再按需增加后端接口检查、前端构建检查或少量关键路径测试。

## Next Test Feedback Format

玩家测试布洛克支线后，建议按以下格式反馈：

- 剧情问题：现在哪里不符合文档，希望改成什么。
- 角色语气：布洛克哪些台词不像，给出期望语气。
- 选择设计：哪些选项缺失、重复、太强或太弱。
- 数值结算：信任值、污染、威胁、奖励是否合理。
- AI 边界：是否剧透、是否越界、是否说了不该说的信息。
- UI 体验：按钮、文本、流程、骰子动画、自由对话是否顺畅。
- Bug：操作步骤、看到的问题、期望结果。

## Assumptions

- 第一幕主流程以 `第一幕大致剧本V2-地心之门.md` 为最高流程依据。
- 同伴支线具体内容以 `第一幕同伴支线事件V1-地心之门.md` 为准。
- 先完成布洛克支线闭环，再扩展到凯娅、莉娅、卡夏、雷铎。
- 所有 AI 自由对话默认不刷信任值，只改变语气和信息深度。
